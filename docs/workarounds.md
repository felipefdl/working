# Workarounds

App code that makes up for something a dependency does not do yet. Each entry stays only until the library can do it; when it can, delete the workaround and its entry.

An entry lists what the workaround does, why the feature is needed, where the code lives, and the upstream change that would remove it.

## Padding around mention highlights

- **What:** a narrow no-break space (U+202F) goes inside both ends of every mention's highlight. A regular space goes outside a mention when a letter or digit touches it ("up@Freddy") and between two mentions that touch. Every highlight, font, and link range is shifted to match.
- **Why:** GPUI paints a text run's background as a box exactly as wide as its glyphs, with no padding and no corner radius. It also joins touching runs that share a background color, so "@Ana@Bia" rendered as one block. Mentions have to read as separate names.
- **Where:** `crates/app/src/message.rs`, `MENTION_PAD`, `mention_marks`, `pad_at`, `shift_start`, `shift_end`, called from `text_segment`.
- **Remove when:** GPUI's `HighlightStyle` (or the text run decoration) supports horizontal padding for backgrounds and stops joining separate runs. Rounded corners need a corner radius on the same background; nothing in the app does that today.

## Bundled color emoji font on Linux

- **What:** the Linux build carries Noto Color Emoji (CBDT bitmaps, from googlefonts/noto-emoji) inside the binary as the family `Working Emoji`, registers it at start-up, and names that family on every emoji: message text and previews are split into runs so each emoji grapheme is a run of its own, and avatars, reactions, the quick reaction bar, the reaction strip, and the emoji picker draw their labels the same way. The window root also lists the family as a font fallback, which reaches text the app does not lay out itself, such as the composer. On Linux the System interface font is the first installed of GPUI's own choices, named, because GPUI drops a font's fallbacks when it resolves `.SystemUIFont`. `scripts/emoji-font.sh` builds the font from a pinned release: it renames the family and maps `m` to the space glyph, and keeps the PostScript name `NotoColorEmoji`. Its license ships next to it and in the AppImage.
- **Why:** GPUI draws Linux text with cosmic-text and swash, and swash cannot draw COLRv1 color glyphs, the only color emoji font Fedora installs (`Noto-COLRv1.ttf`), so emoji and emoji avatars were blank. Installing the bitmap font does not help, since cosmic-text picks the first face named Noto Color Emoji, the system's. GPUI loads a family by name only when it has a glyph for `m`, which emoji fonts lack, and draws a font's color glyphs only when its PostScript name is `NotoColorEmoji`. Naming the family on emoji also draws `❤️` as an emoji: cosmic-text ignores the emoji variation selector and keeps the interface font's black heart. The bundled font is used on every distribution, also where the system font draws, because no system emoji font has an `m` glyph and so none can be named on those runs.
- **Where:** `crates/app/src/emoji_font.rs` (registration, runs, fallback), used from `main.rs`, `root.rs`, `message.rs`, `home.rs`, `ui.rs`, `menu.rs`, `emoji_picker.rs`, and `status_menu.rs`; the System font in `theme.rs` (`SYSTEM_SANS`) and `settings.rs` (`show_theme`, which also leaves the bundled family out of the font list); `crates/app/assets/fonts/`, `scripts/emoji-font.sh`, `scripts/package-linux.sh`.
- **Remove when:** swash or GPUI's Linux text system draws COLRv1 glyphs ([swash#21](https://github.com/dfrg/swash/issues/21), [cosmic-text#446](https://github.com/pop-os/cosmic-text/issues/446), [zed#42255](https://github.com/zed-industries/zed/issues/42255)) and cosmic-text honors the emoji variation selector. Until then, a GPUI that loads a named family without an `m` glyph and recognizes color fonts by their tables instead of one PostScript name would let the app name the system emoji font instead of bundling one.

## Relaunching the AppImage after an update

- **What:** on Linux the restart that finishes an update does not use GPUI's `App::restart`. The app starts its own `bash` script, in a process group of its own as GPUI does, which closes every descriptor above 2 it inherited, waits for the old process to exit, and then `exec`s `$APPIMAGE` with the same environment.
- **Why:** the AppImage runtime keeps the old image mounted, with a helper process and the replaced 28 MB image held open, until every copy of its keepalive pipe closes. That pipe is open in the app without close-on-exec, and GPUI's restart script, then the new app, inherited it, so the old mount stayed until the new app quit, one more for each update in a session. Rust's `pre_exec` or `fcntl` would close it from the app, but both need `unsafe`, which the app keeps to its FFI files.
- **Where:** `crates/app/src/updater/linux.rs`, `RELAUNCH` and `restart`.
- **Remove when:** GPUI's Linux `restart` (`gpui-pre-linux`, `platform.rs`) starts its script with inherited descriptors closed (`close_range` or close-on-exec on all of them). Then `restart` can go back to `cx.set_restart_path` and `cx.restart()`.

## Where the Windows update installer is written

- **What:** at Restart on Windows the app points `tempfile`'s default temporary folder at `%LOCALAPPDATA%\dev.felipefdl.working\updates` (`tempfile::env::override_temp_dir`) before cargo-packager-updater writes and runs the installer, and the next launch removes that folder.
- **Why:** cargo-packager-updater writes the downloaded installer as `%TEMP%\.tmpXXXXXX.exe`, keeps it so it can run it, and never removes it: about 9.4 MB left in `%TEMP%` per update. Its name is random and the process exits right after starting it, so the app could not tell its installer from other programs' files there. In a folder only the updater writes to, the app removes exactly what it wrote.
- **Where:** `crates/app/src/updater/windows.rs` (`run`, `clean`), `gchat_core::updates_dir` in `crates/core/src/paths.rs`.
- **Remove when:** cargo-packager-updater lets the caller choose where the installer goes, or removes it itself (for example by having the installer delete it, or by an `install` that returns its path).

## Upstream limits with no workaround

Problems in a dependency that the app accepts as they are. Nothing in the app makes up for them, so there is no code to delete: each note goes when the library fixes it. Last checked on 2026-11-23 with gpui-kit 0.11.0, gpui-webview 0.11.0, and gpui-fast 0.1.19.

- **Windows: an email is not clipped to the Mail reading pane.** A webview partly scrolled out of the pane draws over the thread's subject line, the Mail toolbar, and the window's top bar, and does not follow its card. gpui-webview 0.11.0 lists a fix ([longbridge/gpui-kit#4066](https://github.com/longbridge/gpui-kit/pull/4066)), and it still happens. Not reported upstream yet. The recheck is an automatic to-do in [AGENTS.md](../AGENTS.md); users read it in [platforms.md](platforms.md).
- **Windows: GPUI drops an event that arrives while a webview is built.** `gpui_webview::WebView::build` waits for `WebView2` by pumping window messages inside a GPUI update. gpui-fast 0.1.19 no longer aborts there ([longbridge/gpui-kit#3984](https://github.com/longbridge/gpui-kit/issues/3984), [longbridge/gpui-fast#145](https://github.com/longbridge/gpui-fast/pull/145)), which is why the app builds webviews in place again. It does not queue the event either: it logs `handling hover status change for window …: RefCell already borrowed` and drops it, so a hover state change can be lost while a webview opens. Seen as about 12 log lines over repeated opens of the viewer and the call window, with no other effect. Not reported upstream yet. If it turns out to lose more than hover, the earlier workaround (building `WebView2` from a task that does not hold the app) is in the history of `crates/app/src/webview/windows.rs`.
- **macOS: an email can flicker over the thread's subject line during a trackpad scroll.** The frames that try a scroll layer use a wider clip for one frame ([longbridge/gpui-kit#4057](https://github.com/longbridge/gpui-kit/issues/4057), open). Not seen with wheel scrolling in a virtual machine, which cannot show a single frame; a trackpad check is an automatic to-do in [AGENTS.md](../AGENTS.md).
- **Linux: a window button can keep its hover color** after the pointer leaves a maximized window through the top edge ([longbridge/gpui-kit#3987](https://github.com/longbridge/gpui-kit/issues/3987), closed upstream). Not rechecked: the test machine's Sway draws no window buttons. It stays in [platforms.md](platforms.md) until it is seen fixed on a desktop that draws them.
