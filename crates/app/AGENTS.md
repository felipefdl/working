# crates/app

GPUI desktop app (`working`). One main window plus optional Meet call windows (macOS and Windows).

## Conventions

- `Store` is the one entity that holds core state and the lists views render. Views own presentation state and send `Command`s; they do not talk HTTP.
- The Mentions and Starred buttons (a sidebar row, a Chats header button, a rail pane) follow `Settings::show_mentions` and `Settings::show_starred`, copied into the `Store` by `sync_settings` so the sidebar items and rail tabs rebuild. A switch hides only the button: an open Mentions or Starred view stays open, and the other ways in keep working.
- Widgets come from gpui-kit (`use gpui_kit::*;` is the kit prelude). Colors come from `theme.rs` through `rgb()`; no literal colors in other files.
- The interface font and the monospace font are `Settings::font` and `Settings::mono_font` (family names; absent is System, and a family no longer installed reads as System, because GPUI panics laying out a missing family). `settings::show_theme` keeps the resolved families in `theme::set_fonts` and on the kit theme's `font_family` / `mono_font_family`, so every setting change restyles every window; the main window and the Meet window roots set `theme::sans()`, and code spans and blocks use `theme::mono()`. System is `theme::SYSTEM_FONT` (`.SystemUIFont`, what GPUI uses with no family: the system font on macOS, Segoe UI on Windows; on Linux the first installed of `theme::SYSTEM_SANS`, named, because GPUI drops a font's fallbacks when it resolves `.SystemUIFont`) and `theme::SYSTEM_MONO`: on macOS `.AppleSystemUIFontMonospaced` (Core Text resolves it without SF Mono in Font Book), on Windows Consolas, on Linux the first installed of `theme::SYSTEM_MONOS` (GPUI matches family names exactly there, so fontconfig's `monospace` alias reads as missing). Never name a font family literally elsewhere.
- Emoji go through `emoji_font.rs`, which does nothing off Linux: `emoji_font::text` for labels that may hold emoji (avatars, reactions, the picker, previews), `emoji_font::runs` over the highlights and font overrides of `StyledText` message text, and `emoji_font::fallback` on a window root. On Linux they draw every emoji with the bundled `Working Emoji` font that `scripts/emoji-font.sh` builds into `assets/fonts/` ([docs/workarounds.md](../../docs/workarounds.md)). New text that can hold emoji uses them too.
- The Calendar view (`calendar.rs`: toolbar, side panel, keys; `calendar_grid.rs`: the six views; `event_card.rs`, `event_editor.rs`: the card and the editor, drawn by the window root as overlays) talks to the core only through the `Calendar*` commands and events held in `Store::calendar`. Its date and lane math is plain code in `calendar_layout.rs` with tests. Event and calendar colors are data (`theme::data_color`, `ink_on`), the one place colors come from outside the theme. Its button follows the layout: a sidebar row (Google Chat), a Chats header button (Messages), a rail button (Rail); all dispatch `OpenCalendar` (`Cmd+2`). `Settings::show_calendar` hides the button only, never the view or its key.
- Message text is drawn with `StyledText`, which cannot be selected. A click on a text bubble (press and release on it, its quote included) opens `text_panel.rs`: a floating panel at the pointer with the raw text in the kit's read-only `Textarea` (select, Cmd+A, Cmd+C, Copy all), drawn by the window root and opened through `text_panel::show`. A link or mention in the text stops the click so it only opens its target, and so does the read-receipt overlay. It closes on Escape (handled first in `RootView::on_escape`), on a press outside, and when the view or conversation changes; while it is open `modal_open` is true. Drop it once the kit's selectable text can carry links.
- The Meet view (`meet.rs`: toolbar, tabs, keys; `meet_body.rs`: the Meetings and Calls tabs and the card with a new meeting's link) talks to the core only through `CreateMeeting`, `StartMeet`, `CreateChat`, and `LoadEvents`, and holds its state in `Store::meet`. The events of its day are a range of their own, apart from `Store::calendar`'s, so each view takes only the answers for its range. A call to someone without a chat makes the chat first: `OpenChat` then posts the meeting in it instead of opening it, and the call is done once the meeting card shows there. What Join accepts, the week strip, and which meetings a day lists are plain code in `meet_logic.rs` with tests. Its button follows the layout: a sidebar row (Google Chat), a Chats header button (Messages), a rail button (Rail); all dispatch `OpenMeet` (`Cmd+3`). `Settings::show_meet` hides the button only, never the view or its key.
- Avatars and attachment thumbnails load through `Images` (core fetch, background decode). Views do not decode bytes on the UI thread or use GPUI's default asset loader for those URLs.
- Read receipts: `Store::receipts` holds the `Event::ReadReceipts` of the open conversation only. An event for it replaces them and only a change reaches `ConversationView::set_readers`, which keeps none while the conversation has receipts off; the next view that is not that conversation drops them, because the core sends them again whenever one opens. Each person's avatar goes on the newest message of the main list, and separately of the thread panel's list, sent at or before their read time (`message::Readers`, over `receipt_logic::place`, plain code with tests: system lines, messages still going out, and failed ones are never the last read, and a person's own messages count). The list is virtualized and measures a row once, so receipts take no part in a row's layout. Every row, read or not, puts the part the avatars sit on (the text bubble, or else the last attachment, or else the last card; never the reactions or the thread footer) in `read_mark`: a row of the part, in a column of its own that keeps the width it would have in the message's column, and a holder (`flex_1`, zero basis) that takes only the room beside it, which is why the message's column fills its row (`flex_1`). The avatars (`readers_group`: 16 px with a 1 px ring in the page color, at most four overlapping and then `+N` in muted text, a tooltip that names them, a click that stops there) lie on an absolutely placed track over the holder, on the part's bottom edge, from 4 px inside the part's bottom corner (bottom-right; bottom-left of the user's own right-aligned bubbles) to 2 px short of the row's edge: beside the part, growing outward, while they fit, else against the track's far end, over the corner. Nothing between the track and the list may clip (`overflow_hidden`).
- Every `cx.observe` / `cx.subscribe` / `cx.observe_global` handle is stored in a struct field; a dropped `Subscription` is a silent no-op.
- Meet runs Google's web app in a webview (`call.rs`, macOS and Windows): `WKWebView` with a Safari user agent on macOS, WebView2 with its own agent on Windows. `call.js` strips the page and drives the controls; the window chrome is ours. Session cookies go into the webview; rotated cookies are written back through `gchat_core::save_session_cookies`. On Windows every webview keeps its data in `gchat_core::webview_dir()`. Linux has no call window: `call::open` there opens the meeting in the default browser, because WebKitGTK as Fedora builds it has no WebRTC.
- The application menus are `root::menus()`, the one list of them: on macOS the system menu bar, and on Linux and Windows the main window's top bar, which has no menu bar. There the bar runs sidebar toggle (when the sidebar is on the left), mark, search field, status and sidebar toggle (when it is on the right), a menu button whose dropdown has each menu as a submenu with its shortcuts, then the kit's window buttons. The right-hand group reserves 150px there instead of macOS's 252px, the width of those three 34px buttons less, so the field stays centered and nothing leaves the window at its 800px minimum width.
- On macOS the app is the only screen-capture client in a call. `screen.rs` opens the macOS picker and captures with ScreenCaptureKit; `call.js` answers Meet's `getDisplayMedia` with a canvas stream of those frames. Never let the webview capture the screen alongside it: macOS gives a picker's answer to one capture client per bundle ID, and the other one's request then never settles. `screen.rs`, `permissions.rs`, and the Settings Permissions section are macOS only; on Windows Meet uses the webview's own screen sharing.
- Sign-in is an in-app webview (`welcome.rs`) that loads Google's account page, writes `cookies.json`, and sends `Command::Connect`. Cookie access for Meet and sign-in is the `session/` seam (`mod.rs`, then `macos.rs`, `linux.rs`, `windows.rs`): it goes to the platform cookie store directly, never through wry's `set_cookie`, which drops the leading dot of `.google.com`.
- Every webview (sign-in, Meet, the viewer) is made with `webview::build`, which hands it to a callback once it is there; never call `gpui_webview::WebView::build` directly. Initialization scripts and the first URL go to `webview::build`, not the builder: on Windows the build runs outside the app borrow and the scripts are added without wry's blocking wait ([docs/workarounds.md](../../docs/workarounds.md)).
- `crates/app/assets/logo.png` and `logo-light.png` are built by `just logo` from `logo/logo.svg`. Edit the SVG, then regenerate.
- Notifications are the `notify/` seam (`mod.rs`, then one file per OS). macOS: Notification Center and the Dock badge, only for the `.app` bundle (`just run`); a bare `cargo run -p working` binary has no notification center. Linux: freedesktop notifications over D-Bus (`zbus`) and the unread count as the launcher-entry signal on `working.desktop`; they are not grouped. Windows: toasts under the `AppUserModelID` `dev.felipefdl.working`, which shows only when a Start Menu shortcut carries it (the installer's), and no badge. Off macOS the sound is Default or None.
- Rewrite tools (`rewrite.rs`) run one headless job with no instruction files, skills, tools, MCP servers, hooks, plugins, or memory. Before adding or changing one, meet [docs/rewrite-tools.md](../../docs/rewrite-tools.md); Grok is out until it has a bare mode.
- The composers' formatting (the bar above a composer's text, shown by the toggle at its right, and `Cmd+B`, `Cmd+I`, `Shift+Cmd+X`, `Shift+Cmd+8`, Ctrl off macOS) writes Google Chat's own markup into the draft: `*bold*`, `_italic_`, `~strike~`, `` `code` ``, `- ` bullets, and three backticks around a code block. The kit's `Textarea` cannot show styled text, so the app sends the draft unchanged and the core turns the markers into formatting on send. What each format does to a text and a selection is plain code in `format_logic.rs` with tests; `conversation.rs` applies it as range edits (`set_selected_range`, then `replace`), never with `set_value` or `replace_all`, so chips stay and undo keeps its history. The kit applies one range per edit, so a format that changes two places (a pair of markers) takes one `Cmd+Z` for each. The keys are bound in the kit's `Input` context in `keys.rs` and act on the composer that has the keyboard, bar shown or not; Shift+8 arrives as the key `*` with the shift folded in, so that binding is `secondary-*`. `Settings::show_format_bar` shows the bar.
