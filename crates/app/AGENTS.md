# crates/app

GPUI desktop app (`working`). One main window plus optional Meet call windows.

## Conventions

- `Store` is the one entity that holds core state and the lists views render. Views own presentation state and send `Command`s; they do not talk HTTP.
- The Mentions and Starred buttons (a sidebar row, a Chats header button, a rail pane) follow `Settings::show_mentions` and `Settings::show_starred`, copied into the `Store` by `sync_settings` so the sidebar items and rail tabs rebuild. A switch hides only the button: an open Mentions or Starred view stays open, and the other ways in keep working.
- Widgets come from gpui-kit (`use gpui_kit::*;` is the kit prelude). Colors come from `theme.rs` through `rgb()`; no literal colors in other files.
- The Calendar view (`calendar.rs`: toolbar, side panel, keys; `calendar_grid.rs`: the six views; `event_card.rs`, `event_editor.rs`: the card and the editor, drawn by the window root as overlays) talks to the core only through the `Calendar*` commands and events held in `Store::calendar`. Its date and lane math is plain code in `calendar_layout.rs` with tests. Event and calendar colors are data (`theme::data_color`, `ink_on`), the one place colors come from outside the theme. Its button follows the layout: a sidebar row (Google Chat), a Chats header button (Messages), a rail button (Rail); all dispatch `OpenCalendar` (`Cmd+2`). `Settings::show_calendar` hides the button only, never the view or its key.
- The Meet view (`meet.rs`: toolbar, tabs, keys; `meet_body.rs`: the Meetings and Calls tabs and the card with a new meeting's link) talks to the core only through `CreateMeeting`, `StartMeet`, `CreateChat`, and `LoadEvents`, and holds its state in `Store::meet`. The events of its day are a range of their own, apart from `Store::calendar`'s, so each view takes only the answers for its range. A call to someone without a chat makes the chat first: `OpenChat` then posts the meeting in it instead of opening it, and the call is done once the meeting card shows there. What Join accepts, the week strip, and which meetings a day lists are plain code in `meet_logic.rs` with tests. Its button follows the layout: a sidebar row (Google Chat), a Chats header button (Messages), a rail button (Rail); all dispatch `OpenMeet` (`Cmd+3`). `Settings::show_meet` hides the button only, never the view or its key.
- Avatars and attachment thumbnails load through `Images` (core fetch, background decode). Views do not decode bytes on the UI thread or use GPUI's default asset loader for those URLs.
- Every `cx.observe` / `cx.subscribe` / `cx.observe_global` handle is stored in a struct field; a dropped `Subscription` is a silent no-op.
- Meet runs Google's web app in a webview with a Safari user agent (`call.rs`). `call.js` strips the page and drives the controls; the window chrome is ours. Session cookies go into the webview; rotated cookies are written back through `gchat_core::save_session_cookies`.
- The app is the only screen-capture client in a call. `screen.rs` opens the macOS picker and captures with ScreenCaptureKit; `call.js` answers Meet's `getDisplayMedia` with a canvas stream of those frames. Never let the webview capture the screen alongside it: macOS gives a picker's answer to one capture client per bundle ID, and the other one's request then never settles.
- Sign-in is an in-app webview (`welcome.rs`) that loads Google's account page, writes `cookies.json`, and sends `Command::Connect`. Cookie FFI for Meet and sign-in lives in `session.rs`.
- `crates/app/assets/logo.png` and `logo-light.png` are built by `just logo` from `logo/logo.svg`. Edit the SVG, then regenerate.
- Notifications and the Dock badge need the `.app` bundle (`just run`). A bare `cargo run -p working` binary has no notification center.
- Rewrite tools (`rewrite.rs`) run one headless job with no instruction files, skills, tools, MCP servers, hooks, plugins, or memory. Before adding or changing one, meet [docs/rewrite-tools.md](../../docs/rewrite-tools.md); Grok is out until it has a bare mode.
