# crates/core

`gchat-core`: session, protobuf API, WebChannel stream, disk cache, and loopback MCP. No GPUI types.

## Conventions

- `src/model.rs` is the public resolved shape (names, byte ranges, absolute URLs). `src/convert.rs` maps wire protobuf onto it. `src/proto.rs` is generated from `proto/googlechat.proto`; edit the `.proto`, never the generated file.
- `proto/googlechat.proto` is the hand-maintained reverse-engineered schema (from purple-googlechat). Add fields when the wire needs them; do not invent names or numbers.
- A request the `.proto` cannot express (such as the starred-message world section) goes through `Http::api_json` in the web app's positional JSON (index `n` is field `n + 1`), copied from a captured web request. Batchexecute RPCs go through `Http::page_rpc`.
- The `API_KEY` in `http.rs` is the public Chat web app key. Keep it. Attachment downloads omit `Origin` and `Referer`: with them, Google answers 204.
- Google Calendar (`src/calendar.rs`) is not the Chat API: it calls the documented Calendar v3 JSON at `clients6.google.com`, signed with `SAPISIDHASH` headers made from the session's SAPISID cookies (origin `https://calendar.google.com`), plus the browser key found on the calendar page. Opening a session loads that page once through the account redirects, which sets the calendar's own cookies; the first key the API accepts is kept. A 401 opens the session again once. Writes go through `Command::SaveEvent`, `DeleteEvent`, and `RespondEvent`; `WORKING_READONLY=1` refuses them. The demo answers them in `demo/calendar.rs`. `cargo run -p gchat-core --example probe` reads the calendar, and `WORKING_PROBE_CALENDAR_WRITE=1` (without read-only) also creates, renames, and deletes one private test event.
- A meeting of its own (`Command::CreateMeeting`, Meet's "New meeting") is the Chat API's `create_video_call` without a `group_id`, the call `StartMeet` makes before it posts the result: `Http::api` as for every Chat call (session cookies, XSRF token, the public `API_KEY`; none of Calendar's SAPISIDHASH or page key). The server makes the meeting space and answers a video call annotation that nothing posts, so the meeting is in no conversation and on no calendar; the link is its `meeting_space.meeting_url`, `https://meet.google.com/<code>`. Every `CreateMeeting` gets one `Event::MeetingCreated`, an `Err` being short enough to show (the cause goes to the log); `WORKING_READONLY=1` refuses it that way. The demo answers it in `demo/mod.rs`. `WORKING_PROBE_MEET_CREATE=1` (without read-only) makes the probe create one empty meeting and print only the shape of its link.
- A message goes out as typed: `Command::Send` and `Edit` carry the composer text with Google Chat's markers (`*bold*`, `_italic_`, `~strike~`, `` `code` ``, three backticks for a block, `- ` or `* ` for a bullet), and only `src/markup.rs` reads them. It answers the text without the markers, the chips moved to match, and format spans; `convert::format_annotations` puts the spans on the create and edit requests and `convert::pending_spans` on the message shown at once. The demo and the MCP `send_message` use it too; the app never reads markers.
- Read receipts (`Event::ReadReceipts`) come from `list_topics`, which asks for `FetchOptions::ReadReceipts`, and from the stream's `READ_RECEIPT_CHANGED`; both carry a `ReadReceiptSet`: whether receipts are on, and per person the time they have read up to (everything sent at or before it; live, usually the exact time of the last message they read). The event never lists the signed-in user, resolves people like a message's sender (the wire profile, else the users map), puts the earliest reader first, and is empty when receipts are off (many conversations have them off). It goes out just before the `History` it belongs to, again when `Command::Open` or `Command::Jump` shows what is held (the app keeps the receipts of the open conversation only, so it needs them each time one opens), and only when it differs from the last one sent. A load answer replaces what was sent; a stream event may name only the people who just read, so it is merged (a person's time never moves back, a known name stays). Nothing is cached on disk. The demo sends it in `demo/mod.rs` (its members have read to different recent messages, whoever starts typing a reply has read the newest one, and an app's conversation has receipts off); the probe prints only counts for it.
- Timestamps are `Micros` (microseconds since Unix epoch), as Chat reports them.
- Cache writes go through the atomic temp-file rename in `cache.rs`.
- MCP listens on loopback only. The secret is `~/.config/working/mcp-token`. Tools stay few and named for a person request; a `conversation` argument accepts a name or an id. `WORKING_READONLY=1` still refuses sends even when `allow_send` is true. `send_message` goes only to a conversation read with `read_conversation` since the last send (`Reads`, shared by every client because the server keeps no sessions).
