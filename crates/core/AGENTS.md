# crates/core

`gchat-core`: session, protobuf API, WebChannel stream, disk cache, and loopback MCP. No GPUI types.

## Conventions

- `src/model.rs` is the public resolved shape (names, byte ranges, absolute URLs). `src/convert.rs` maps wire protobuf onto it. `src/proto.rs` is generated from `proto/googlechat.proto`; edit the `.proto`, never the generated file.
- `proto/googlechat.proto` is the hand-maintained reverse-engineered schema (from purple-googlechat). Add fields when the wire needs them; do not invent names or numbers.
- A request the `.proto` cannot express (such as the starred-message world section) goes through `Http::api_json` in the web app's positional JSON (index `n` is field `n + 1`), copied from a captured web request. Batchexecute RPCs go through `Http::page_rpc`.
- The `API_KEY` in `http.rs` is the public Chat web app key. Keep it. Attachment downloads omit `Origin` and `Referer`: with them, Google answers 204.
- Google Calendar (`src/calendar.rs`) is not the Chat API: it calls the documented Calendar v3 JSON at `clients6.google.com`, signed with `SAPISIDHASH` headers made from the session's SAPISID cookies (origin `https://calendar.google.com`), plus the browser key found on the calendar page. Opening a session loads that page once through the account redirects, which sets the calendar's own cookies; the first key the API accepts is kept. A 401 opens the session again once. Writes go through `Command::SaveEvent`, `DeleteEvent`, and `RespondEvent`; `WORKING_READONLY=1` refuses them. The demo answers them in `demo/calendar.rs`. `cargo run -p gchat-core --example probe` reads the calendar, and `WORKING_PROBE_CALENDAR_WRITE=1` (without read-only) also creates, renames, and deletes one private test event.
  - Event reminders (`Command::WatchEvents(true)`; nothing reads the calendars for them before it) run `Engine::event_watch`: the next 24 hours of events every 5 minutes and after each calendar write, sleeping until the next notification time between reads. The timing is the plain `calendar::due_reminders` and `next_reminder`: a regular event or focus time, at a time of day, not declined by the user, and starting after the watch began; `Reminder::Minutes(n)` comes n minutes before the start, `Reminder::Default` at the calendar's own popup (the first `{"method":"popup","minutes":n}` of the calendar list entry's `defaultReminders`, kept by `Client::calendars`; none when the calendar has none), `Reminder::None` never. Each event id and start reminds once (a moved event, with a new start, again); one found late still comes until a minute after its start, with `minutes` 0 once it started. Off aborts the task, and what it told is forgotten with it.
- Gmail (`src/mail.rs`) is neither the Chat API nor the official Gmail API (that one refuses cookie auth). It calls the sync JSON the Gmail page itself uses: `POST mail.google.com/sync/u/0/i/bv` for a mailbox's threads, `.../i/fd` for a thread's emails, and `.../i/s` for the changes it makes (mark read or unread, archive or move to the inbox, move to Trash, star or unstar, put on or take off the user's own labels, send a reply, send a new email (with bcc too), forward an email, save a draft and send it later). Opening a session loads `mail.google.com/mail/u/0/` once with a jar of the `.google.com` and `accounts.google.com` cookies (the redirects through accounts.google.com and `SetOSID` set Gmail's own); landing anywhere but mail.google.com means signed out. The page's `_GM_setData` key `w43KIf` gives the `x-framework-xsrf-token` value (`[1]`, whole) and the id key (`[2]`); `GLOBALS[2]` and `GLOBALS[3]` (the build label) fill the captured `x-gmail-btai` template with the user agent, offset, and time zone; `sBEv4c` `[6][1][0]` is the send-as identity `[email, …, name at 4]` (else `GLOBALS[10]`, the email alone). A 400 or 401 (or an `["er",…,400|401,…]` answer) opens the session again once, which fetches a new token. Every answer index is a named path in `mail.rs`; the map:
  - `bv` request: the captured template, `[0][3]` the query (`in:inbox`, `is:starred`, `in:sent`, `in:all`, `in:<label id>` for a label, or the search text), `[0][1]` the page size, `[0][9]` the page index (page `n` starts at thread `n × size`; later pages can answer a few more threads and overlap, so appending dedupes by id). Answer `[2]` threads newest first (null when none), `[11][0]` 1 when older threads exist, `[6][0]` rows `[label, unread, total]` (the `^i` row's unread is the inbox badge, the same number as the Atom feed's `fullcount`).
  - Labels: every list answer carries `[1]`, rows `[[id, name, …], n]`. The user's own have `[0][17] == 2` (Gmail's are 5, categories 1, others more) and ids `^x_…`; `[0][1]` is the full name with `/` between parents and children; `[0][14]` is `[text, background]` as `0xRRGGBB` numbers, absent without a color (the label's color is the background); its unread count is its `[6][0]` row. `in:^x_…` lists a label's threads by id, so names with spaces, slashes, or accents need no escaping. `MailLabels` is sorted by name, case-insensitively.
  - A thread `[[subject, snippet, ms, id, [messages oldest first], …], n]`; a message `[id, [1, email, name?], …, ms at 6, …, labels at 10, attachments at 11]`. Unread: a message labelled `^u`; starred: `^t`; files: an attachment with `[0][0] == 1` (`0` is an image inside the HTML; `^fhas` is not attachments). A name comes trimmed and without one pair of wrapping quotes (`mail::clean_name`): Gmail leaves some as `"Jordan Park"`, `'Jordan Park at jpark@example.com' via Team`, or with a lone leading apostrophe.
  - `fd` request `[[[id, 1]], 2]`, which leaves the thread unread. Answer `[1]` entries `[id, [summary, [message summaries]], [[message id, detail]], …]`: the entry's `[1][0][1]` is the thread's subject; a summary `[id, from, ms, labels, …]` (a draft Gmail holds, not sent, carries `^r`: `MailMessage::draft`); a detail `[to, cc, bcc, reply-to, subject, [null, [parts]], snippet, Message-ID, [References], In-Reply-To, …, attachments at 13, …]`, the HTML being every part's `[2][1]` in order; bcc (`DETAIL_BCC`, `MailMessage::bcc`) is carried only by the user's own sent emails. An attachment `[[regular, part id, 1, [image, url, name, mime, size, …]], …]`; its absolute `mail.google.com` URL (and an inline image's `view=fimg` URL in the HTML) needs Gmail's cookies, so it is fetched through `mail::Client::fetch`.
  - `s` (a change): `[null, [[[op index, [thread id, payload]], …]], [1, sync version, null, null, [null, 0], null, 1], [earlier ms, op count, now ms, 1 when it sends, 90], 2]`; the answer `[[[[op index, code, null, new sync version], …]], …]`, code 0 accepted. Gmail takes any op index (1 in a fresh session) and any sync version (0 or stale), so the session counts its own. A label change is payload `[6] = [[added], [removed] | null, [message ids]]` (`OP_LABELS`); the ids are required (without them the answer is still 0 and nothing changes), so a change reads the thread with `fd` first, and a thread whose read finds no emails (one Gmail does not have) is refused before anything goes. Mark read: add `^o`, remove `^u` `^us` on every email; mark unread: add `^u` on the newest; archive: add `^a`, remove `^i`; move to inbox: add `^i`, remove `^a`; move to Trash (`Client::trash`): add `^k` and remove `^i` on every email, using the mailbox labels from the [captured thread Delete](https://github.com/KartikTalwar/gmail.js/blob/548667244dc12b7417ba83fddff8c350bbb7881e/test/testdata-parser.js); star (`Client::star`): add `^t` on the newest email only, as Gmail's star does (`[["^t"], null, [newest id]]`); unstar: remove `^t` from every email (`[[], ["^t"], [all ids]]`); the user's labels (`Client::label`): add and remove their `^x_…` ids on every email (`[[added], [removed] | null, [all ids]]`), and `mail::check_user_labels` refuses any other id, or nothing to change, before anything goes. A reply is saved as a draft in its thread first (payload `[1] = [message as a draft]`, `OP_SAVE_DRAFT`, as Gmail's reply box does; see signature placement below), then sent with payload `[13] = [message, answered message id, 1, null, [now ms]]` (`OP_SEND`); the message's slots (`SENT_*` in `mail.rs`) carry a client-minted `msg-a:r<random i64>`, from, to, cc, subject, the body as parts `[[0, written html], [2, Gmail's quote]]`, the labels a send carries (`^pfg` pending, then Gmail makes it `^f` sent), In-Reply-To (the answered detail's Message-ID), kind `[74]` 2, flags `[42]` `[0, 0, 0, null, 0]`, and the session's `s:<16 hex>|#<id>|0`. A new email (`Client::compose`) is two changes on a thread id the client mints (`thread-a:r<random i64>`, `mail::new_thread_id`): first payload `[2] = [[subject, null, now ms, thread id, [message as a draft]]]` (`OP_CREATE`) makes the thread (the draft carries `^all ^r ^r_bt ^io_im ^io_imc3` and no kind), then payload `[13] = [message, null, 1]` sends that same message (same id; kind 1, flags `[0, 0, 1, null, 0]`, `[0, 0, 0, null, 0]` when signed, only the written part, no In-Reply-To), which turns the draft into the sent email. Slot `[4]` (`SENT_BCC`) is bcc, the same address shape as to and cc, left out when empty; it was found by sending, not from a capture of the web client (live: the hidden recipient got the email, its copy shows only the `To` address and no Bcc header, and Gmail's `fd` records it as bcc). Replies carry no bcc. A forward (`MailForward`, `Client::forward`) is not the web client's forward, whose request was never captured: it is a new email on a new thread, sent as a compose is (kind 1, `OP_CREATE` then `OP_SEND`, `Session::send_new`), with subject `Fwd: ` and the thread's (not doubled, `mail::forward_subject`), the written part what the user wrote, then Gmail's forwarded block (`mail::forwarded_html`: `<div class="gmail_quote gmail_quote_container">` with the `gmail_attr` lines `---------- Forwarded message ---------`, From, Date, Subject, To, and Cc when there are copies, then the email's HTML). It reads the thread with `fd` first and refuses a message id not in the thread, or a draft. Attachments are not carried, and an image inside the email that needs Gmail's cookies does not show for the recipient (live: the recipient got the header block and the quoted email). An agent's draft is the first of those two steps alone (`Client::save_draft`: `OP_CREATE` for a new email, `OP_SAVE_DRAFT` for a reply, checked as a send is) and answers what its send needs (`mail::Draft`: the built message, its thread, the answered id, to, cc, bcc); `Client::send_draft`, any time later, is the second step (`OP_SEND`) with that message, exactly as saved. A draft is saved once: Gmail accepted a second save under the same id but kept showing the first wording, so saving over a draft is never sent, and discarding one is the user's, in Gmail. A send into a thread Gmail does not have yet is refused (live: code not 0). Gmail keeps only the sent copy of mail to oneself, so a reply, new email, or forward the user is a recipient of (bcc included) also carries `^i` (never `^u`, though the web client marks a new email to oneself unread). Before anything goes, `mail::check_recipients(to, cc, bcc)` wants someone in any of the three and each a plausible `local@domain` (trimmed), with a short error to show. The web client's thread-view op, its `^io_*` marks, its repeated draft autosaves, and the opaque token op after each send (payload `[25]`, about 1.5 KB, not protobuf) are not sent.
  - `MailMessage::text` is `mail::html_to_text`: hidden elements dropped, block elements on their own lines, entities decoded. `mail::html_to_text_unquoted` is the same text without the earlier emails it quotes (Gmail's `gmail_quote` blocks and `<blockquote type="cite">`), `None` when it quotes nothing or the quote is all it has.
  - What the user writes goes out as Gmail's compose writes it (`mail::written_html`, for new emails and replies): each line its own `<div>…</div>`, an empty line `<div><br></div>`, all inside `<div dir="ltr">`, never `<p>` (which other mail clients draw with margins). The demo's `html_of` writes its emails the same way, lists aside.
  - Signatures (`mail::page_signatures`, read with the session's page, so a new session reads them again). The formatted signatures are in the page's `_GM_setData` key `w4hJLd`, a JSON string of rich settings whose `[0][0]` is a list of `[number, {extension id: value}]`: extension `221494602` (entry `"105"` live) holds `[[signatures], [picks]]`, each signature `[id, null, name, [null, html]]` and each pick `[address, id for new emails, id for replies]` (an empty id is "No signature"; the live account picks the same signature for both, so which slot is which follows the settings page's order, not a seen difference); extension `138780968` (entry `"61"`) holds per address `[address, [null, html]]`, used when there are no named signatures. The address's own entry wins (the signed-in address, compared without case), else the first. `MailSignature::text` is `html_to_text` of that HTML, so bold reads as the word. In `sBEv4c`, the entry tagged `"p"` holds the plain settings as `[name, value]` string pairs: `bx_se` `"1"` is the signature switch (absent before one was ever set; off means no signature at all), `bx_stw` is "Insert signature before quoted text in replies and remove the "--" line" (`"1"` on), and `sx_sg` is only Gmail's plain-text rendering of the default signature (bold as `*word*`, the reason the first build sent asterisks), kept as the last fallback when the rich settings have none (escaped, lines joined with `<br>`). The send-as entry (`cfs`) has an empty slot where its scripts keep a signature; not read.
  - Signature placement (`mail::signature_block`, `SignaturePlace`, `reply_body`) is what Gmail's web client sent in recorded signed emails (a new email without text, one with text, and a reply): `<div><br clear="all"></div>` (the empty first line Gmail's compose window opens with, which a new email's text takes the place of, so a new email with text has no such line), then `<div><br></div><span class="gmail_signature_prefix">-- </span><br>`, then `<div dir="ltr|rtl" class="gmail_signature">` around the signature's HTML, with ` data-smartmail="gmail_signature"` in a new email and without it in a reply. A new email's goes inside the written part's `<div dir="ltr">` after the text (flags `[42]` `[0, 0, 0, null, 0]`, as Gmail's signed ones); a reply's at the end of the quoted part, after Gmail's quote; with `bx_stw` on, above the quote in the written part as `<div><br clear="all"></div><div>…</div>` without the `-- ` line (from Gmail's scripts; not seen sent). A reply is sent as Gmail's reply box sends it: first saved as a draft in its thread (payload `[1] = [message as a draft]`, `OP_SAVE_DRAFT`), then that same message is sent. Sent without the draft, Gmail's server cut the signature out into a body part of kind 3 ("SIGNATURE", which its reader draws in gray `font`); with the draft it stays in the kind-2 quoted part, as in Gmail's own reply (live, on the test thread). A signed new email with text comes back from Gmail's server as `[0 text][3 signature][0 </div>]`, Gmail's own exactly the same (live: Gmail's reader draws its own signature gray too; the black one is the compose editor's draft). Only with `MailReply::signature` or `MailCompose::signature`, and only when the account has one; otherwise the email goes as before. The engine tells `MailSignatures` after the first inbox page that read well and again when a session gives others (`MailHeld::signatures`; `StopMail` forgets them). The demo's Avery has a made-up one for new emails and a shorter one for replies, told with the first inbox and added the same way (`signature_block`) with the plain text under `-- ` in `MailMessage::text`.
  - The engine (`Engine::load_mail` and around it) holds each mailbox's threads with the pages read; `LoadMail { more }` reads the next page index and appends without repeats. The first inbox `LoadMail` shows `mail.json` (the inbox's first page, `cache::MailCache`) before Gmail answers and starts the watch: the inbox's first page every 60 s, merged over the older pages held, told with `MailThreads` only when it changed. `MailUnread` comes from the `^i` label row of any list answer when it changed, and `MailLabels` from the label rows of any list answer (the first one included) when a label or a count changed; `MailIncoming` from `mail::Arrivals` (unread, newer than the first load, once per newer message). Every failure is `Event::MailFailed`, never `SignedOut` (Chat may still work); the watch tells a failure once until a read works again. `StopMail` aborts the watch, forgets what is held, labels included (answers already on the way are dropped by a generation number), and closes the session; `mail.json` stays. `Core::fetch` sends `mail.google.com` URLs through `mail::Client::fetch` and keeps only image bytes in the image cache.
  - Obligations of the mail client: it sends only `GET mail.google.com/mail/u/0/` (the page), `POST /sync/u/0/i/bv`, `/sync/u/0/i/fd`, and `/sync/u/0/i/s` for exactly the changes above (on the thread the user or an allowed agent acted on, or the new thread of a new email, a forward, or an agent's new-email draft), and GETs of attachment and image URLs from an answer. Label changes are only those above: read, unread, archive, inbox, Trash, the star, and the user's own labels (`^x_…`, never Gmail's). Drafts are only the one a new thread is made with, the one a reply is saved as right before it is sent, and an agent's draft, saved once and sent later exactly as saved. A forward is a new email as above, never the web client's forward, and its files are not carried. No permanent delete, no spam, no making or deleting a label, no saving over or discarding a draft, and never the web client's bulk removal of `^us`. `WORKING_READONLY=1` refuses every change, and a change needs Mail on (`Engine::mail_on`). MCP's mail write tools exist only with `McpConfig::mail_write`. It never opens Gmail in a browser (the web client clears unseen marks). It never logs or prints cookies, tokens, or mail text (the probe prints counts and step names only). Live checks of a change run only on the test thread `Working write capture` or on a new thread sent to the signed-in address, a reply, a new email, or a draft only to the signed-in address (a new email's check uses the subject `Working compose check`, `Working signature check`, or `Working MCP mail check`); a bcc or forward check may also send to the user's own other address, with the subject `Working MCP mail check` or as a forward of the test thread. `WORKING_PROBE_MAIL_WRITE=1` drives the probe's mark and archive steps on the test thread; with `WORKING_MCP_PORT` it also runs, through the mail MCP tools, star and unstar on the test thread, a reply draft there saved and sent (only when it goes to the signed-in address alone), and a new-email draft to the signed-in address saved and sent (subject `Working MCP mail check`). Fixtures use made-up people (`Jordan Park`, `jpark@example.com`), never anything from a real mailbox. A change of Gmail's shapes is fixed in the named paths at the top of `mail.rs` and in the map above, which is where the derived field map lives; its tests are hand-written fixtures in those shapes.
  - Engine writes (`MarkMail`, `ArchiveMail`, `TrashMail`, `ReplyMail`, `ComposeMail`): each shows its change at once in the held lists, the open thread, `MailUnread`, and label counts, then writes, then answers `MailWritten(Ok(()))`; a failure puts back what it changed, tells it again, and answers `MailWritten(Err(..))` with a safe text. A sent reply reads its thread again (`MailMessages`) and marks the thread as the user's own for `mail::Arrivals`, so it never counts as new mail. A new email shows once Gmail has it: the engine mints its thread id when the command comes (so `Arrivals` knows it as the user's own from the start, never `MailIncoming`), and after the send reads again the held lists it belongs in (Sent and All Mail, and the inbox when the user is a recipient; `Engine::show_composed`), which tells them when they changed; lists never asked for stay unread. `mail::reply_recipients` (exported) gives a reply's `to` and `cc` as Gmail's Reply and Reply all do. Archiving keeps the thread it took out of the inbox list (`MailHeld::archived`), so moving it back puts it in at once, in time order; when the engine holds no copy of it anywhere, the inbox is read again right after the write instead of at the next poll. `mail::Changes` keeps each change (read, unread, archived, trashed, starred) and lays it over every list answer asked for before Gmail had it (its threads, and the inbox count when the answer is the inbox's; another list's inbox count and label counts are left out until a later answer), so a write made before the first network inbox answer, or racing a poll, still ends with the right threads and counts; it has no overlay for labels. Changes are forgotten 2 minutes after Gmail had them, or at once when it refused them. Only agents star, label, and draft (`Engine::agent_star`, `agent_label` with `^x_…` ids only, `agent_draft`, `agent_send_draft`, no `Command`): a star or label shows at once in the held lists (`MailThread::starred`, the held Starred and label lists, label unread counts when certain), is put back on failure, and the held lists it touched are read again after the write. `agent_draft(MailDraft)` saves a new email or a reply in Gmail's Drafts and answers the draft's id (its message id `msg-a:r…`); the engine holds what its send needs in memory (`MailHeld::drafts`, by message id: the built message, thread, answered id, to, cc, bcc), through `StopMail`, until Working restarts, after which the draft is still in Gmail's Drafts for the user to send there. `agent_send_draft` sends a held draft exactly as saved and answers `MailDraftSent` (to, cc, bcc, thread); a sent draft is forgotten, a failed send keeps it. Only agents forward, too (`Engine::agent_forward`, `MailChange::Forward`): the engine mints the new thread's id, `Client::forward` reads the email's thread with `fd` and refuses an id not in it or a draft, and after the send it does a compose's follow-up reads (`Engine::show_composed`, the user's own for `Arrivals`); it answers the new thread's id. Moving a thread to Trash removes it from held lists immediately. After success the engine rereads the inbox and held searches so Gmail decides which searches still include it.
  - Every sync call has its own deadline (`READ_TIMEOUT` 20 s for `bv` and `fd`, and for the page a session opens with; `WRITE_TIMEOUT` 30 s for `s`), and a call that runs out answers "Gmail did not answer in N s" (a list then answers `MailFailed`), never an endless Loading. The client pings idle HTTP/2 connections (every 20 s) and drops pooled ones after 60 s idle, so a request is not sent on a connection the network dropped. Reads run each in its own task and never wait behind a write or another read; only opening a session (the page load, once, or again after a 400 or 401) holds the others until it is done. With `WORKING_TRACE=1` each call logs its kind and milliseconds (`Gmail bv: 284 ms`) and the session open its time, never content. Live, a first page of `in:all` (50 threads) answers in about 0.3 s, like the inbox, so it keeps the page size of 50 the web client also asks for.
  - Every mail command gets exactly one answer, which the view waits for: `LoadMail` its `MailThreads` (even when nothing changed; a `more` with nothing older, or with the next page already on its way, answers what is held at once, `MailList::next_read`) or `MailFailed`; `OpenMail` its `MailMessages` or `MailFailed`; each write its `MailWritten`. Signed out (`wait_for_session`), reads answer `MailFailed("Sign in to start.")` and writes `MailWritten(Err(..))`. The one exception is `StopMail`: answers still on their way are dropped, since the app forgets every list and request with it.
  - `Event::MailWritten` handling: the writes run one at a time through `Engine::mail_writer`, in the order their commands came; each answers its `MailWritten` (and a reply its `MailMessages`) before the next write starts, and a refused command (read-only, Mail off) is queued too, so its answer keeps its place. So the app can match each `MailWritten` to its commands in order: one answer per `MarkMail`, `ArchiveMail`, `TrashMail`, `ReplyMail`, or `ComposeMail`. The demo answers each command at once, in the same order; its `ComposeMail` puts a thread from Avery on top of Sent (and of the inbox, read, when Avery is a recipient), refuses no recipient or a wrong address with the real client's text, and the workspace person who is the first recipient answers back once, 15 s later, as after a reply.
- A meeting of its own (`Command::CreateMeeting`, Meet's "New meeting") is the Chat API's `create_video_call` without a `group_id`, the call `StartMeet` makes before it posts the result: `Http::api` as for every Chat call (session cookies, XSRF token, the public `API_KEY`; none of Calendar's SAPISIDHASH or page key). The server makes the meeting space and answers a video call annotation that nothing posts, so the meeting is in no conversation and on no calendar; the link is its `meeting_space.meeting_url`, `https://meet.google.com/<code>`. Every `CreateMeeting` gets one `Event::MeetingCreated`, an `Err` being short enough to show (the cause goes to the log); `WORKING_READONLY=1` refuses it that way. The demo answers it in `demo/mod.rs`. `WORKING_PROBE_MEET_CREATE=1` (without read-only) makes the probe create one empty meeting and print only the shape of its link.
- A message goes out as typed: `Command::Send` and `Edit` carry the composer text with Google Chat's markers (`*bold*`, `_italic_`, `~strike~`, `` `code` ``, three backticks for a block, `- ` or `* ` for a bullet), and only `src/markup.rs` reads them. It answers the text without the markers, the chips moved to match, and format spans; `convert::format_annotations` puts the spans on the create and edit requests and `convert::pending_spans` on the message shown at once. The demo and the MCP `send_message` use it too; the app never reads markers.
- Read receipts (`Event::ReadReceipts`) come from `list_topics`, which asks for `FetchOptions::ReadReceipts`, and from the stream's `READ_RECEIPT_CHANGED`; both carry a `ReadReceiptSet`: whether receipts are on, and per person the time they have read up to (everything sent at or before it; live, usually the exact time of the last message they read). The event never lists the signed-in user, resolves people like a message's sender (the wire profile, else the users map), puts the earliest reader first, and is empty when receipts are off (many conversations have them off). It goes out just before the `History` it belongs to, again when `Command::Open` or `Command::Jump` shows what is held (the app keeps the receipts of the open conversation only, so it needs them each time one opens), and only when it differs from the last one sent. A load answer replaces what was sent; a stream event may name only the people who just read, so it is merged (a person's time never moves back, a known name stays). Nothing is cached on disk. The demo sends it in `demo/mod.rs` (its members have read to different recent messages, whoever starts typing a reply has read the newest one, and an app's conversation has receipts off); the probe prints only counts for it.
- `Group::mentioned` (the unread activity mentions the user, `Message::mentions`) has no wire signal: `convert::group` yields false and the engine keeps it. Every group change goes through `Engine::update_group`, `upsert_listed`, or `rebuild_groups`, which all end in `engine::settle_mention`: false while read; else a held history that is loaded and reaches back past `last_read_time` decides it alone (a message from someone else, newer than the cursor, that mentions the user), and short of one the flag the stream set stays while the read cursor does not move. A history page that changes it publishes the group (`Event::GroupUpsert`). Once the list is in at startup, after `Command::Connect`, and after the stream comes back from offline (`sync_world_and_mentions`), `Engine::seed_mentions` reads the newest page of the Mentions search once (no paging, leaving the shortcut's hits, cursor, and `mentions.json` alone; also under `WORKING_READONLY=1`) and marks, through `update_group`, each listed unread conversation with a hit from someone else newer than its `last_read_time` (`engine::seeds_mention`). That search answers direct @mentions only, never @all (checked read-only against a live account), so an @all that arrived while the app was closed is told only by the conversation's history.
  - History prefetch (`Engine::prefetch_histories`, at startup from the cached list and again once the list is in, and after `Command::Connect`; three `list_topics` at a time) loads what the plain `engine::prefetch_order` picks: first the listed (not hidden, not blocked) unread conversations not loaded yet, newest first, muted ones included (a muted conversation shows as unread only once it mentions the user); then the rest of the 16 most recent (`PREFETCH_RECENT`) not loaded yet; at most `PREFETCH_MAX`, which is `HELD_HISTORIES` (24), since each one past what memory holds pushes an earlier prefetched history out again. Each prefetched page settles the mark through `refresh_history`'s `settle_held_mention`. An unread conversation past the cap shows an @all only once its history loads (opened, or a later prefetch). The probe prints the counts of listed, unread, muted, and mentioned conversations and of the histories that arrived. The demo derives the mark from the messages it holds.
- The conversation actions (`Command::SetPinned`, `SetMuted`, `SetNotify`, `MarkUnread`, `SetHidden`, `SetBlocked`, `MoveToSection`) change the held group and publish it before the request goes out. On failure they put the old value back and send a short `Event::Error`, with the cause going to the log. `Leave`, `DeleteConversation`, and blocking a space (which also leaves it) take the group off `Event::World` only once the server agrees. `WORKING_READONLY=1` refuses them all, and the demo answers them. The wire formats were captured from the web client:
  - `<triple>` is `["space/<id>", "<id>", 2]` or `["dm/<id>", "<id>", 5]`. Pin is page RPC `XZhsdc` `[<triple>, 1|0]`. Hide is page RPC `n7ICcf` `[<triple>, 1|0]`. Delete a space is page RPC `U3Vwwb` `[<triple>]` (`engine::delete_arguments`).
  - Block is page RPC `BFhA9d`: a space `[null, <triple>, 1, 0]`; a DM's other person `[["<user>", "human/<user>", 0], null, 1, 0, null, <triple>]`, unblocked with `[[...], null, 0, null, null, <triple>]`. Unblocking a space, blocking a group DM or an app, and deleting a 1:1 DM were not captured and are refused.
  - Leave is `remove_memberships` with the signed-in user's own id as the one `member_ids` entry.
  - Mute and notification level are `update_group_notification_settings`: `{1: GroupId, 2: {2: room_state, 3: {1: 2 mute | 1 unmute}}}`. Muting echoes, unchanged, the raw `room_state` of the held `paginated_world` item (left out only when it has none). A level sends its raw `room_state` (4 all, 5 main conversations, 2 mentions, 3 none; the proto enum names only 0–3, and the server reports 4 and 5 too) with the current mute state. `convert::notify` reads the raw value.
  - Move to a section is `apply_group_label` `{1: {1: CUSTOM_SECTION, 2: "<section id>"}, 2: GroupId}`, after `remove_group_label` with the same shape for the user's section it is in; back to its kind's section is the removal alone. The web client was never seen removing the Meetings label (`predefined_meeting_chat`), so a meeting chat only gains the new label and is never moved back to its kind's section.
  - Mark unread is `set_mark_as_unread_timestamp` `{1: GroupId, 2: usec}`, with the newest message time. `MarkRead` sends it with 0 first when the held item carries a mark.
  - Hidden and blocked groups stay in `Event::World` with `Group::hidden` / `blocked` (from `hide_timestamp` and `blocked`); the app decides where to show them. They never count as unread, never notify (`MessageUpsert::incoming` is false), and are left out of MCP and history prefetch. A new message in a hidden group asks for the list again, so the server decides whether it comes back. A group the user left or deleted leaves the world (`convert::is_member`). `Group::can_delete` is a space whose `membership_role` is `ROLE_OWNER`.
  - The demo mirrors this: hidden and blocked groups stay with the flag (a new message brings a hidden one back), `Leave`, `DeleteConversation`, and blocking a space remove the group, and `MoveToSection` uses the sections in `demo/data.rs` (`SECTIONS`). "Coffee chat" is the demo's deletable space.
- Timestamps are `Micros` (microseconds since Unix epoch), as Chat reports them.
- Cache writes go through the atomic temp-file rename in `cache.rs`.
- The demo's pictures are JPEGs in `src/demo/photos/`, embedded with `include_bytes!` and listed in `demo/image.rs` with the size their attachments declare (`demo:image/<file>`). They are AI-generated, never downloaded: each one's prompt and date go in `photos/README.md`. Keep each file a 4:3 or 3:2 landscape JPEG, long edge about 1600 px, metadata stripped, the set under about 1 MB.
- `src/paths.rs` is the one place that knows where files go on each OS (`config_dir`, `cache_dir`, `scratch_dir`, and on Windows `webview_dir`); in demo mode `config_dir`, `scratch_dir`, and `webview_dir` point under the temp dir. Cookies and the MCP token are written with `paths::create_private` (mode 0600 where the OS has modes). Short-lived files with the account's content (an attachment open in the viewer, a pasted picture) go to `scratch_dir()` through `write_private` (folder 0700, file 0600), never to the system temp dir, which other users of a Linux machine share; the app empties the folder when it starts.
- `cookies.json` has three writers, all through the merge in `lib.rs` (one at a time, by cookie name, domain, and path): the sign-in, a Meet call's rotated cookies, and the chat side itself. `Http`'s jar (`SessionJar`) keeps what Google sets on its answers (`SIDCC` and its like, on ordinary requests) and `Engine::session_loop` writes that to the file every two minutes, so a later launch or Meet call starts from the session as it is, not as the sign-in left it. A copy of the file on another machine (a VM, an agent's browser) is not kept in step: what that copy's use changes reaches this file only when its `cookies.json` is copied back. When Google refuses the session with the saved cookies too, `Http::note_refused` adds a line to `session.log` beside the file (the time, and the file's age; never a cookie's name or value).
- One sign-in serves Chat, Gmail, and Google Calendar, so a refusal by any of them signs the whole app out. Gmail and Calendar open their own sessions (`mail::Client`, `calendar::Client`) through `http::ServiceSession`: when the page they ask for lands on Google's sign-in page (`http::asks_sign_in`), the client answers `SignedOut`, `Event::SignedOut` goes out, and `session.log` gets a line naming the service, once until the session opens again. Any other failure stays a `MailFailed` or `CalendarFailed`. The sign-in (`welcome.rs` `session_looks_complete`, `scripts/login.sh`) saves only a session that has the `accounts.google.com` sign-in cookies (`LSID` and its kin): without them Chat opens and Gmail and Calendar are sent to sign in.
- MCP (`src/mcp/`) is one server per product on one loopback listener, each switched on by itself in `McpConfig`: chat at `/mcp/chat` (`chat.rs`), mail at `/mcp/mail` (`mail.rs`), calendar at `/mcp/calendar` (`calendar.rs`), Meet at `/mcp/meet` (`meet.rs`); `shared.rs` holds the loose argument parsing, the tool result, and the words for times and text every server uses. Each is a whole MCP endpoint in both protocol revisions with its own name (`working-chat`, `working-mail`, `working-calendar`, `working-meet`), its own instructions, and only its own tools. `mod.rs::admit` checks a request in this order: the origin (403 for a web page), the path (404 for `/mcp`, an unknown name, or a server that is off, before the secret is looked at), then the secret, `mcp-token` in `config_dir()`, as a bearer header on the server's path or the next path segment (`/mcp/mail/<token>`); 401 without it. With every server off nothing listens. Tools stay few and named for a person request, and call `pub(crate)` engine accessors, never `Command`s, so they work without the app having opened that product.
  - Chat: `inbox`, `recent_activity`, `find_conversations`, `read_conversation`, `search_messages`, and `send_message` only with `allow_send`. A `conversation` argument accepts a name or an id. `WORKING_READONLY=1` still refuses sends even when `allow_send` is true. `send_message` goes only to a conversation read with `read_conversation` since the last send (`chat::Reads`, the chat server's own, shared by every client because the server keeps no sessions).
  - Mail: read tools, always listed: `mail_inbox` (`mailbox`, or a `label` by name; `limit` default 20, at most 50; `unread_only`; `page` default 1), `mail_search` (`query`, `limit`, `page`), `mail_read_thread` (`thread`; `message` one email by its id, `last` the newest N, `quotes` default false), `mail_labels`, and `mail_attachment` (`thread`, `message`, `file` by name or 1-based number), calling `Engine::mail_threads`, `mail_messages`, `mail_labels` (the labels as last told, else read from the inbox), and `mail_file` (`mail::Client::fetch`), and leaving the lists the app holds alone. Page n reads `Engine::mail_threads(mailbox, n - 1)`, 50 threads a page; the answer ends with the call for the next page, and Gmail's later pages can repeat a few threads. `mail_read_thread` gives each email's id, leaves out the earlier emails it quotes (`mail::html_to_text_unquoted`) unless `quotes`, prints a `Bcc:` line where Gmail has one (`MailMessage::bcc`, only on the user's own sent emails), marks a draft (`MailMessage::draft`) as a draft not sent, and numbers each email's files. `mail_attachment` refuses a file over 25 MB, saves it with `paths::write_private` under `paths::scratch_dir()` (the folder 0700, the file 0600; the app empties it at start), and answers its name, type, size, the path on its own line, and for a text type (`text/*`, JSON, XML, CSV) its text (HTML through `html_to_text`). With `mail_write` also `mail_send` (`to`, `cc`, and `bcc` as a list or one text with commas, `Name <address>` or the address; `subject`, plain `text`, `signature` default true; checked as `ComposeMail` is, before anything goes; answers the new thread's id, naming hidden copies apart), `mail_reply` (`thread`, `text`, `reply_all`, `message` default the newest sent email not from the user, else the newest sent; never a draft; recipients only from `mail::reply_recipients` of that email: the tool takes none, and a `to` is refused; answers who it went to), `mail_forward` (`thread`, `message` default the newest email that is not a draft, `to`, `cc`, `bcc`, `text` may be empty, `signature` default true; `Engine::agent_forward`; answers who it went to, how many attached files were left out, and the new thread's id), `mail_draft` (a new email: `to`, `cc`, `bcc`, `subject`, `text`, `signature`, checked as `mail_send`; or with `thread` a reply: `text`, `reply_all`, `message`, `signature`, recipients as `mail_reply`, never from the call, and `to`, `cc`, or `bcc` refused; `Engine::agent_draft`; answers the draft id, who it would go to, and the `mail_send_draft` call; each call makes a new draft), `mail_send_draft` (`draft`; `Engine::agent_send_draft`, the draft exactly as saved; a draft not held, sent or saved before Working restarted, is refused and is still in Gmail's Drafts for the user), `mail_archive` (`archive` default true, false moves back to the inbox), `mail_mark` (`read` required), `mail_star` (`starred` default true), and `mail_label` (`add`, `remove`: names of the user's existing labels, resolved with `find_label` against `mail_labels`; making a label is not offered). `mail_archive`, `mail_mark`, `mail_star`, and `mail_label` take `thread` as one id or a list, write each in turn, list what was done and what failed, and are an error only when none succeeded. Not offered: delete, spam, making or deleting a label, saving over or discarding a draft, and carrying attachments on a forward. The writes are refused, in this order, when `mail_write` is off ("Writing mail is turned off…"), under `WORKING_READONLY=1`, and with Mail off. They go through the app's own write path (`Engine::agent_compose`, `agent_reply`, `agent_forward`, `agent_draft`, `agent_send_draft`, `agent_archive`, `agent_mark`, `agent_star`, `agent_label`: the ordered write queue, the change shown at once in the held lists, the follow-up reads), so the app's lists follow an agent's write; each waits for Gmail and answers success or the failure, through its own channel (`MailJob::Write::answer`), never `Event::MailWritten`, which the app matches to its own commands in order. The server instructions say once what every tool shares: tools answer only while Mail is on in Working, reading leaves threads unread, writes are real and immediate. All tools answer only while Mail is on in the app (`Engine::mail_on`: an inbox `LoadMail` started the watch and no `StopMail` came since); otherwise they answer the error "Mail is turned off in Working." without contacting Gmail. They stay listed either way, since Mail turns on and off while the server runs and clients keep the list (a settings change, such as `allow_send` or `mail_write`, restarts the servers). The demo serves no MCP ("Agents are off in demo mode.").
  - Calendar: `calendar_list`, `calendar_events` (a range, default today and the next 7 days; a calendar and words filter), `calendar_get_event`, reading through `Engine::calendar_list`, `calendar_events`, `calendar_event`. With `calendar_write` also `calendar_create_event`, `calendar_update_event` (only what it names changes, from the event as it is), `calendar_delete_event`, `calendar_respond` (accept, decline, maybe), through `EventDraft`, `EditScope`, and `Rsvp` (`Engine::calendar_save`, `calendar_delete`, `calendar_respond`); `notify` defaults to false, an event that repeats needs `scope`, and `WORKING_READONLY=1` refuses them. After an agent's change the reminder watch and the range the app shows read the events again (no `CalendarWritten`).
  - Meet: `meet_create_meeting` (`Engine::create_meeting_link`, the meeting `Command::CreateMeeting` makes; refused under `WORKING_READONLY=1`) and `meet_upcoming` (the next 7 days' calendar events that have a Meet link). The core offers nothing else for Meet.
